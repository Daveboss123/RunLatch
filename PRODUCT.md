## 1. Product and target user

**8 November implementation addition:** read-only `/intelligence` projects selected LOCAL receipt axes, exact evidence-matched provider spend/finished-run cohorts/failed costs/blocked attempts/comparable canonical quote changes, plus an explicitly UNATTESTED manual fixture validator. Illustrative data is separately selected and labelled. [Reproduction and limits](docs/OUTCOME_RECEIPTS_AND_INTELLIGENCE.md); exact checks/failures in BUILD_LOG.md section44. Earlier counts above cover the earlier observation candidate only; no independent chain/provider truth, public wallet or release clearance added.

RunLatch is **outcome-bound purchasing and financial accountability for AI-powered businesses**: delegate a project task, bind purchases to current human authority and full commercial terms, and inspect what was approved, paid, received and checked.

**Beachhead:** small owner-led AI-native software/automation agencies and digital/creative studios delivering client work. This is an unvalidated customer hypothesis, not adoption/market evidence. The MVP is one operator/fictional organisation, not a hosted multi-tenant service.

**Problem:** a budget alone does not answer whether the client work is still active, which vendor/plan was approved, whether another agent already acquired it, what future obligations exist, whether payment settled, or what delivery evidence the client can inspect.

**Product hypothesis:** project context + Client Work Capsule + commitment-aware quote-bound Gate + Outcome Receipts + Project Expense and Outcome Report. Spending limits/agent wallets/project budgets alone are not novel. No customer adoption, superiority, verified savings or formal AP2 compatibility claimed.

**Promise:** “Give an AI agent a job, not a blank cheque.” Public copy must qualify supported rails, source/network, owner trust and check scope; no generic wallet positioning or end-to-end delivery guarantee.

## 2. Named concepts

| Concept | Meaning |
| --- | --- |
| Project | Client/internal work-order reference, owner-authenticated status/revision, immutable ceiling and outcome definition; sensitive labels off-chain |
| Client Work Capsule | Existing capsule evolved: funded task authority bound to project/revision, exact agent/key, caps/scope/expiry and immutable policy/hash |
| Gate | Rust contract checks that decide `APPROVED`, `APPROVAL_REQUIRED`, or `DENIED` |
| Registered quote | Immutable provider-authenticated vendor/recipient/plan/resource, amount due now, bounded full commitment, cadence/term/cancellation metadata, expiry/version/hash |
| Outcome Receipt | Distinct authorisation/payment/provisioning/check/human-acceptance axes with provenance and unavailable evidence explicit |
| Project Expense and Outcome Report | Read-only owner-selected disclosure derived from canonical records; no client account system or public private-data sharing |
| Project intelligence | Transparent project expense/commitment totals; prior cost-per-success remains a secondary research-regression measure |
| Replay Lab | Repeatable adverse requests and settlement tests, with their execution source visible |

Rulebook, notifications, and provider reputation are later concepts, not required empty navigation pages. The explicit 7 November request authorizes a local [policy compiler/editor](docs/POLICY_WORKSHOP.md): deterministic instructions/manual terms, typed validation, exact owner review and immutable local versions. It is not a new spending-authority path or a connected LLM/signing service.

The subsequent [contract observation demo](docs/CONTRACT_OBSERVATION_DEMO.md) connects `/demo` to explicitly imported LOCAL agency records. The scoped scripted agent reads registered quotes and submits only bound IDs/hash; Rust loads canonical payment terms. The browser checks internal record/evidence consistency, prepares unsigned drafts and shows separate payment/provisioning/check/acceptance axes. It does not execute purchases, independently establish chain truth or enable owner signing. Public-testnet integration remains unavailable.

## 3. MVP scope and ordering

### Must deliver

1. One Rust NEAR contract with a human-controlled operator and a separate authorized agent account/key.
2. Owner-authenticated bounded project status/revision and funded capsule creation. Policies remain immutable; material changes invalidate old authority, never silently rebind approvals. Total original capsule allocations cannot exceed the immutable project ceiling; no recursive or revolving allocation.
3. Controlled database/hosting demo providers with immutable one-use quotes. Research search/extraction and third-provider failure fixtures remain separately labelled regression scenarios, not simultaneous marketplace vendors.
4. Rust checks direct identity, active project, current project/capsule reference, expiry, canonical quote/vendor/recipient, full commitment, resource duplicates, scopes, integer budgets, replay and exact approval. Unknown/unbounded charges fail closed; new fixed-term recurring commitments require approval by default unless explicitly forbidden.
5. Exact owner approval/rejection/cancellation for eligible pending requests. No pending-approval reservation; no approval bypass of a hard denial.
6. Pre-funded native NEAR **testnet** transfers with reservations and honest success/failure callbacks. Owner reclamation of unused purchase funds follows a separate safe close operation, not a task-quality refund.
7. One fictional agency/client website work order: purchase a canonical database fixture, wait for proven native settlement, record clearly labelled provisioning fixture, run a predeclared objective resource/website check. Preserve the20–50-record research workflow as regression, not the primary story.
8. Receipts separate decision, submission, settlement, provisioning, task check and explicit owner acceptance. Owner report anchoring proves who recorded it, not honest execution/external truth. Acceptance is a separate authenticated action, not implied by validation PASS.
9. Replay Lab: altered quote, replay, stale/cancelled project, exact resource duplicate, hidden fixed-term commitment, cumulative/concurrent budget and payment failure/quarantine. Source labels always visible.
10. Read-only owner-selected project expense/outcome report: settled spend, reservations, future commitments, available-now vs available-to-commit, vendor/plan/purpose and evidence scopes. Totals come from canonical records, never LLM summaries.
11. A clear, accessible RunLatch interface and product-first landing page with the required Roster reference and central dithercn visual system.
12. Reproducible setup/tests, explicit limitations, genuine testnet evidence, and the human-approved repository/demo/submission materials required by the live rules.

**Implementation order:** direction reconciliation -> project/revision contract tests -> project/capsule foundation -> canonical commitments/duplicate controls -> settlement extensions -> evidence/acceptance/report workflow -> core UI -> Replay Lab/QA -> approved testnet demo/release. Existing tested mechanisms are reused, not restarted.

### Not in the MVP

- Mainnet, real money, stablecoins, swaps, Intents, Chain Signatures, bridging, recurring collection, or conditional payment for overall task success.
- A general provider marketplace, external vendor acceptance claims, multi-agent negotiation, hosted signer/relay, multi-tenant accounts, or database/indexer infrastructure.
- Mandatory paid AI inference, private inference/TEE, reputation/opaque success scores, automatic policy activation, SaaS cancellation/renewal execution, subscription-management suite, ERP/invoicing/client portal or extensive analytics. The newly requested local policy workshop is the explicit exception to the earlier compiler deferral; Rust authorization and immutable-capsule boundaries do not change.
- Production custody guarantees, delivery guarantees, refunds for poor output, formal security audits, comprehensive fraud detection, or factual verification of arbitrary research.
- Heavy 3D, chart widgets, stock assets as product evidence, decorative metrics, or overlapping animation/design packages.

Optional extensions are conditional tests in ACCEPTANCE_TESTS.md, not permission to implement them or mandatory release blockers when absent.

## 4. Primary demo and preserved regression

Fictional **Northstar Studio**, **ACME Demo Client**, **Automated Booking Website**. Use native NEAR integer demo amounts in a300:50:20 ratio; the brief's $300/$50/$20/$240 are commercial illustrations, not a guaranteed token value or implemented fiat rail. Database purchase -> actual supported settlement -> fixture provisioning -> objective check -> optional explicit owner acceptance -> selected report. Adverse attempts must include altered quote/replay and recurring/full-term or stale-project denial.

Fixed recurring fixture20 per period ×12 =240 full commitment. When50 has already settled from300 and another20 is committed,240 no longer fits. Show due-now separately and evaluate full authority; do not claim real SaaS acceptance/automatic collection/cancellation. Provider adapters declare fixture mode, payment rail/cap/provisioning/cancellation/signature capabilities.

### Historical research workflow (regression, not primary positioning)

**Workflow identifier:** `research-fixture-v1` is an implemented LOCAL scripted fixture ID, not a live service.

The local runner selects a registered search quote, waits for confirmed payment, obtains controlled search-fixture records, selects an extraction quote, waits for payment, and produces a structured report. A failure fixture produces an incomplete/malformed report to demonstrate paid-but-failed validation.

Provider fixtures are intentionally controlled demo services. Their files may be publicly inspectable for reproduction; this is not a production paywall or proof that third-party API vendors accept testnet NEAR.

**Credential-free fallback:** scripted proposals and local provider/validator fixtures require no optional AI API key. They are labelled scripted/local. Real testnet execution still needs separately approved accounts, a scoped agent signer, funding, and deployment; “no AI key” does not mean “no signing authorization.”

An optional LLM can later propose purchases through the same constrained schema. It is never the Gate, cannot call owner/provider methods, and cannot change quoted terms.

## 5. User journeys

### Owner: define authority

1. See the execution mode, network, wallet account, and actual contract configuration.
2. Enter task, budget, per-purchase limit, exact provider/service scope, agent account/public key, expiry, approval threshold, and validation specification.
3. Schema and cross-field checks highlight invalid or unknown values. No inferred provider, recipient, budget, or expiry silently becomes trusted.
4. Review exact policy and separate storage funding; explicitly sign capsule creation/funding only after approval.
5. Inspect current allocated, spent, reserved, and available amounts. Pause stops new authorization; resume is allowed only while unexpired and unfinished. Revocation cannot be undone.

### Workflow: purchase within the capsule

1. Read a canonical quote/hash; propose capsule/request/quote plus bound project/current revision. Resource identity and commercial terms are not agent-selected payment fields.
2. The contract authenticates the account/key and evaluates canonical state. Browser previews cannot authorize funds.
3. Hard failure: deny with reason codes, no purchase reservation/transfer. Blockchain execution failures are shown separately from structured Gate denials.
4. Soft approval threshold: show approval pending, holding no capacity. The owner reviews and approves the exact stored request; all mandatory rules are checked again.
5. Authorization: atomically reserve canonical amount due now, separately retain future commitment, claim canonical project resource and consume the quote before transfer scheduling. Pending approval holds none of these.
6. Confirmed failure: release the purchase reservation and retain the failed request; retry requires a fresh quote/request. Unknown callback outcome: retain pending funds, stop unsafe retries, show reconciliation needed.

### Owner: understand outcome and close

1. The fixed validator checks the produced file under its versioned criteria; output, method, reason codes, and artifact hash are inspectable off-chain.
2. Owner attestation, when signed, anchors that reported outcome and stops new purchases. No unfinished settlement may be hidden by marking the run complete.
3. A settled payment can coexist with failed task validation. Validation does not undo payment or promise refunds.
4. Inspect an Outcome Receipt, actual transaction/receipt references, and a genuinely denied attempt.
5. Reclaim unused immediate funds only once outgoing payments are resolved, excluding retained future-commitment collateral. Closing/refund failure remains explicit. No timer/owner quality decision cancels an obligation; no supplier-cancellation integration exists.

### Judge / visitor

Explore labelled local previews without credentials; inspect deployed testnet records when available; use documented local commands for the scoped workflow and attack scenarios. Public pages do not carry a shared spending key. No fake login or inert “run” button hides this boundary.

## 6. Outcome definition and first metric

Primary `website-resource-fixture-v1` checks exact project/resource manifest binding, fixture provisioning/health200/HTTPS flag and `/health`/`ok` fixture route/body at a recorded time. It does not contact a website/database or prove external deployment. Separate owner acceptance binds the outcome and current provisioning snapshot; later evidence preserves historical acceptance but can mark it stale. Reports keep other purchases explicitly NOT_CHECKED.

Project totals disclose settled spend, pending funds, committed future, available-now/to-commit and original allocation/returns. A denied20×12 request exposes240 as proposed commitment but adds no money/commitment. Report defaults to no financial/expense/evidence disclosure; no client login/public sharing service. This is a canonical-input projection, not an independent chain verifier.

### Retained research metric (secondary regression)

`research-output-v1` checks strict JSON structure, required fields, at least 20 and at most 50 distinct records, valid HTTPS URL syntax, and deterministic fixture expectations. Exact schema/hashes are specified in ARCHITECTURE.md. Network reachability, if later added, has a different criteria version and cohort.

**Completed run for analytics:** an immutable terminal validation attestation exists, authorization is stopped, and no purchase/refund settlement is unresolved. Include passed, failed, and error results in the completed cohort; exclude unfinished/unattested/unknown runs and report their count.

**Cost per successful run:** total settled provider-purchase spend across **all completed runs in the same cohort**, including failures, divided by the number with validation passed. If none passed, show “not available,” not zero/infinity. Failed-run costs are not discarded.

Group by workflow, validation criteria/version, validator version, asset, and network. Show period, sample size, success/failure/error counts, exclusions, and numerator/denominator. Purchase spending excludes gas, storage credit, and owner refunds. No statistically conclusive or causal provider-quality claim from the small demo sample.

## 7. Trust boundaries and risks

| Component / risk | What it establishes | What it does not establish / mitigation |
| --- | --- | --- |
| Model / scripted runner | A proposal was generated | Not authority; validate data and restrict the key and methods |
| Operator policy | Human authorized exact rules | Not perfect natural-language interpretation; manual review and immutable activation |
| Provider registration and quote | Registered account published canonical terms to its pinned recipient | Not honesty or delivery; disclose controlled catalogue and operator registration trust |
| Contract | On-chain rules, reservations, and supported native-transfer accounting | Not arbitrary external facts or protection against a human-held deployment key replacing code |
| Scoped agent key | Restricted receiver/method and gas exposure | Not business budget, key expiry, or human identity; contract checks account/key/capsule and deadline |
| Validator and owner attestation | A named/versioned off-chain checker reported a result which the owner attested | Not independent consensus, factual truth, or automatic refunds |
| Hashes and receipts | Binding/change detection and evidence links | Not confidentiality, originality, causal quality, or proof an unattested report is truthful |
| RPC / explorer | Observed final state and transaction/receipt responses | Not a trustless light client; cross-check critical demo evidence and disclose source/block |
| Async failure | Ordinary failed transfer can reconcile in a healthy callback | Callback failure can leave funds quarantined; no unsafe timeout release; evidence-backed recovery is unresolved and out of the baseline |
| Storage / gas | Bounded funded operations | Not free transactions; pre-fund history and report limits/fees honestly |
| Scope / deadline | One demonstrable loop is feasible in principle | Environment and integration remain unproven; prioritize contract tests over optional pages/protocols |

## 8. Release definition and unresolved decisions

A working revised MVP is a reproducible project-bound testnet purchase, several contract-blocked adverse requests including full-term/stale/duplicate controls, honest failure/quarantine tests, independently labelled provisioning/check/acceptance facts and canonical selected-scope report in a polished interface. It is not a wallet dashboard or fabricated infrastructure integration.

Local implementation is autonomous; approved Linux tools already work. Before release: confirm name/license/eligibility, exact public account/key/deployment/run consent, real evidence, public links, clean-start tests and live rules. No public action is authorised by this document.

### Personas and jobs

- Owner/operator: defines client work, fixed budget, vendor/category/cadence/term authority and disclosure; reviews full obligations and project margin, not just the first charge.
- Project lead/reviewer: owner role in the MVP; explicitly pauses/cancels work, reviews eligible exceptions, evidence and human acceptance.
- Agent: proposes typed purchases/claims; never changes policy, approves itself, impersonates a human or declares settlement/truth.
- Client: report recipient only; no RunLatch account required. Reports omit keys, prompts, operational identities, confidential terms and unrelated projects unless explicitly selected and safe.
- Cancellation outside RunLatch is not magically known: an authenticated owner must update project state. Multiple agents cannot bypass the project ceiling by creating capsules/children.
