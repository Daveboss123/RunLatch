## 4. Typography and copy

- Space Grotesk 500/600 for headings; Inter400/500/600 for body/controls; IBM Plex Mono400 for exact data. Human explicitly requested Roster's font pairing on7 November, superseding the DM Sans proposal. Self-hosted Fontsource5.3.0 Latin variable/mono assets and unmodified OFL notices; current exact bytes/hashes in BUILD_LOG.
- Self-host approved font assets under `public/fonts/`, with required license notices. Avoid remote font requests and layout shift. Do not default to Inter for every role.
- Proposed scale: hero 40–72px fluid, section heading 28–44px, subsection 20–24px, landing body 16–18px, operational body 14–16px, compact data 13–15px. Do not shrink important amounts or warnings to fit a row.
- Headings about 1.05–1.15 line height, body about 1.5–1.65. Prose generally 55–75 characters per line. Align operational content left and amount columns right.
- Use tabular digits and stable columns; show full decimal-string amounts on inspection/copy. Display rounding must never change the authorized amount.
- Sentence-case labels and plain verbs: “Approve purchase,” “Pause capsule,” “Inspect receipt.” Keep the same action name across button, confirmation, and result.
- Explain a denial specifically, with a next step that does not suggest bypass: “This quote has expired. Request a new quote.” Pending copy explains what remains unknown.
- No jargon-only hero, decorative all-caps eyebrows, tracked labels above every heading, gradient text, isolated italic/accented headline words, or monospace used as ornament.

## 5. Layout and responsive behavior

Mobile-first with normal document flow. The content—not a device name—determines the breakpoint. Use CSS Grid and component/container adaptation where useful; do not install a layout framework.

| Width / situation | Required behavior |
| --- | --- |
| 320–479px | Single column; 16–20px gutters; hero promise then board; actions wrap/stack; readable trace/receipt; local horizontal scroll only for genuinely wide tables |
| 480–767px | 24px gutters; compact two-column summaries when labels fit; no forced side-by-side financial inspector |
| 768–1023px | 24–32px gutters; board or workbench may use two regions; app navigation stays reachable without clipping |
| 1024px+ | 32–48px gutters, centered max 1240px; deliberate hero/product relationship; wide comparison and table surfaces |
| Zoom/text enlargement | Preserve actions and labels at 200% zoom; reflow prose at narrow effective widths; never hide policy/amounts to make it fit |

- Baseline section spacing approximately 64px on phones and 96–128px on wide screens; tighten related elements while varying section proportions.
- No page-wide horizontal overflow. A wide table gets a labelled, keyboard-reachable scroll region; key status/amount/inspect action remains understandable.
- A mobile menu is a real button with labelled open/close state, focus handling, and Escape behavior. Do not add a disabled hamburger or offscreen-only navigation.
- Sticky app controls must not overlap content, focused elements, or the footer. Public header behavior is chosen deliberately after reference review, not sticky by default.
- IDs may wrap/truncate visually with copy/full inspection; never truncate the only available recipient or amount in a signing review.
- Test 360, 390, 768, 1024, and 1440px, plus 320px/zoom reflow. Real browser screenshots at 1440 and 390px are mandatory; record failures rather than claiming coverage.

## 7. Status and evidence language

Use text/icon/source labels, not color alone:

| Axis | States / display rule |
| --- | --- |
| Evidence source | `SIMULATED`, `LOCAL`, `TESTNET`; distinguish scripted proposals, SDK unit mocks, Sandbox, and public-network evidence in detail |
| Capsule authority | Active, paused, revoked, expired, completed, closing, closed; “completed” is neutral until validation is shown |
| Decision | Approved, approval required, denied; approval is not payment success |
| Transaction | Not submitted, submitted, included, final, failed, unknown; a business denial can be a successfully executed transaction |
| Purchase payment | Not attempted, settlement pending, settled, settlement failed; unknown callback remains pending with “needs reconciliation” |
| Provisioning | Not evidenced, fixture/application-observed, failed, unknown; show source/method, never infer it from payment |
| Task/validation | Not checked, passed, failed, error; exact objective scope/time and LOCAL/owner-attested provenance |
| Human acceptance | Not recorded, accepted/rejected by explicitly authenticated owner; never implied by agent assertion/PASS |
| Owner refund | Separate from purchase settlement; pending/returned/failed, with net allocated and returned amounts |

Green means a specific confirmed fact, never universal run success. Amber text uses the accessible warning-text token. A receipt can say **“Purchase settled; validation failed.”** Quotes/IDs/hashes can be inspected and copied without putting secrets or prompt contents in URLs.

Budget visualization keeps exact string labels: net allocated, settled, pending reservation, committed future, available-now and available-to-commit plus returned. A segment partition uses spent+reserved+future+available-to-commit; available-now overlaps future and must not be added as a second segment. Original funding adds returned separately. No invented rolling balances or fiat peg; critical values remain text.

### Theme mapping

- `--dither-paper` -> paper (or panel on a panel); `--dither-ink` -> ink, not shadcn's lime primary by accident.

### Rendering, motion, and safety

- Static SVG patterns/CSS masks for fills, bars, dividers, small surfaces, and fallbacks; image dithering only for an actual needed image. No mandatory image asset for the MVP.

## 9. Interaction, accessibility, and performance

- Use semantic landmarks, headings, links/buttons, forms, tables/captions, labelled dialogs, and readable check traces. Aim for WCAG 2.2 AA behaviors; do not claim certification.
- Normal text >=4.5:1, large text >=3:1; focus/control/meaningful graphical boundaries >=3:1 where applicable. Test against the densest dither region, not average background.
- Keyboard-only navigation with visible focus, no traps, appropriate tab/arrow semantics, Escape dismissal, and restored focus. Do not remove browser outlines without an equivalent.
- Touch targets preferably at least 44px in both dimensions; compact table actions keep generous target padding.
- Error text identifies the field/check, preserves safe input, and explains correction. Owner actions provide pending/cancel/error/success states, prevent duplicate submissions, and refresh canonical state after completion.
- Loading skeletons never invent a balance. Empty states offer a genuine action. Stale/RPC-unavailable data is explicitly labelled and cannot imply current authority.
- Announce meaningful status changes once through a polite live region; do not narrate every numeric animation or shader frame. Critical errors are readable and not auto-dismissed.
- Motion defaults: 120–180ms control feedback, 180–260ms disclosure/state change, occasional 300–500ms public reveal. All are proposed upper ranges, not requirements to animate every element.
- Numeric text updates atomically to the confirmed value; a short highlight is safer than rolling financial digits. No fake “request -> approved -> settled” sequence while awaiting evidence.
- No scroll-jacking, parallax dependence, continuous dense animation, delayed access, heavy 3D, remote analytics, or indiscriminate Motion/Recharts/TanStack installs. Start with CSS, semantic tables, and static engine fills.
- Test actual bundles, loading/layout shifts, console, network requests, CPU/GPU work, reduced motion, and fallbacks. State measured results, not fabricated performance numbers.
