# Local sequential nonce reconciliation

**8 November 2026. Local injected evidence only; the Working testnet MVP remains incomplete.** The restricted-agent exercise can now use the same ephemeral key for up to three distinct requests, advancing only after an explicitly supplied exact prior reconciliation. No real key, public transaction, wallet or provider execution is enabled.

## What changed

- `scripts/near/local-nonce-reconciliation.ts` recomputes the captured ordinary V0 transaction hash from its public unsigned fields, then reuses `inspectPurchaseEvidence` for the exact call, canonical transfer, private callback, final record and receipt-graph checks. The transaction's RPC-shaped numeric nonce must equal the captured decimal-string nonce. Both access-key query envelopes must match the evidence context's final block hash/height. The existing restricted-access inspector checks the exact ordinary key, nonce/list agreement, one receiver/submit-only method, positive finite capped allowance and recovery-key presence.
- The current key nonce must equal the prior signed nonce, not merely be greater. Only finalized settled/confirmed-failed purchase evidence, or an exact finalized denial/rolled-back initiating call with no purchase transfer, can produce an **issued in-memory local reconciliation**. Inclusion, hash acknowledgement, unknown transaction, approval-pending, unresolved transfer/callback, a retained pending record or `reconciliation_required` cannot advance.
- `scripts/near/local-sequential-key.ts` uses the **unchanged one-shot key guard as a permanent anchor** in the same namespace/directory/account-key domain. A legacy one-shot claim cannot be adopted, released or reset by this coordinator. New sequential runs append bounded exclusive claim/capture files; they never replace the anchor or an earlier attempt.
- `forRun(prior)` supplies an actual issued reconciliation for each next run, including after restart. The next issued review must match its target/key/allowance/recovery scope and exact nonce, be no older than that observation, and use a different request. The saved previous identity must match the observation. Historical marker contents alone never grant another nonce. Cloned/JSON-reloaded reconciliation results are rejected.
- The existing composed runner, request journal, ephemeral signer, codec and broadcaster are unchanged. A request claim is still synced before the key claim, and verified identity/capture/entry before one injected send. The original request claim remains consumed even if its send was unknown and later exact local final evidence allows a **different** request. Nothing updates that original transport result or resends it.

## Sequential record model

An account/key gets at most three slots in this deliberately narrow demo exercise: `0`, `1`, `2`. Each has one `.seq.<slot>.claim.json` and one `.seq.<slot>.signed.json`, under the existing `key-guard/<namespace>/` directory. There are at most eight files per key including the original two anchor markers. Each read/write is bounded to16KiB; scans visit only these fixed paths, not an unbounded directory listing. Claims bind their exact public transaction, preceding signed-marker hash and supplied reconciliation; captures bind their claim hash and verified public transaction hash/fields. Reads check contiguous slots, marker shapes, byte/hash agreement and the permanent anchor.

Exclusive `wx` creation and file sync precede a returned lease. An issued in-memory lease is required for capture; its stage is consumed before asynchronous I/O. Concurrent processes/coordinator instances competing for the same next slot produce one winner. An interrupted claim, partial capture, malformed/oversized/orphan marker, I/O fault or missing anchor is fail-closed. There is no delete/reset/release, stale-lock age, nonce refresh, replacement signature or recovery-by-changing-namespace path. A fourth run is refused; increasing this bound or migrating a prior one-shot claim is not admitted by this milestone.

Files contain public transaction/review identifiers and a bounded reconciliation summary only, not private keys, signed wire bytes, artifacts, prompts or untrusted failure messages. File hashes detect inconsistencies, not malicious rewriting by a local attacker. Directory/regular-file/symlink and handle checks reduce accidental redirection; these checks are not an atomic OS sandbox, distributed lock, network-filesystem guarantee or power-loss durability proof. Deliberately deleting markers/changing namespaces/workspaces can evade local state and is not supported recovery.

## Evidence and API limits

This constructor accepts **trusted local test inputs** with `INJECTED_TEST_TRANSPORT_NOT_CHAIN_EVIDENCE`. It has no HTTP transport/default fetch or public entry point. Labelling arbitrary records with that string does not establish chain truth. The existing read-only testnet reader remains unchanged; an admitted adapter still needs to collect these records with exact query scope, same-final-block pinning, current/historical code checks and bounded failure/cancellation behavior. No light client, account-key control proof or authenticated human consent is supplied here.

NEAR's transaction view and access-key responses use numeric nonce fields. Unsafe JSON integers are rejected using the existing safe-integer checks, never cast/repaired through `Number`. The narrow codec still supports u64 decimal strings; that does not mean the RPC read path admits every u64 number. Money and purchase commitments stay decimal strings/checked integers. RPC hash/field matching is not independent byte reconstruction of a transaction view or settlement truth without the underlying chain reads.

Current official Context7 `/near/docs` access-key/transaction-execution docs confirm ordinary key nonce acceptance in `(current_nonce, block_height*10^6]`, nonce replacement on inclusion and height-derived nonce initialization when adding a key. This implementation chooses **exact observed nonce+1**, not block-height-derived speculative values. A changed/reinstalled key, higher nonce or external signer activity is divergence and remains blocked. Gas-key lanes are unsupported. Node24 exclusive-create, bounded FileHandle read/stat and sync documentation was checked before implementation.

The stricter resolved-purchase requirement is intentional: transaction nonce consumption alone is distinct from transfer/callback resolution. No reconciliation function changes contract spend, reservations, future commitments, project authority, provisioning, task checks or human acceptance. A confirmed contract failure/denial is not an automatic retry. Approval-pending remains blocked in this conservative exercise even though it holds no purchase reservation.
